# PGO 与热点实验（2026-10-24）

> 目标：用 3 轮 PGO 迭代看能不能把批量对局跑快；顺便用 profile 找到真正的热点。
> 结论先行：**本机 aarch64 上 PGO 没有稳定收益，不启用**；热点在 AI 寻路，
> 下一步应该做源码级缓存/网格化，而不是编译器 PGO。

## 1. 结论

1. PGO1（480 局训练）在 40 局核心场景的 paired ratio 约 0.98–1.17，
   多数批次约 1.10（略慢）；200 局长跑约 0.967（略快）——**基本持平，没有稳定胜出**。
2. PGO2（累计 930 局）/ PGO3（累计 1380 局）在同一批次内分别慢约 **47% / 53%**，
   且与 AI 决策函数被内联膨胀一致：
   `raider::decide` 12,992 B → 30,340 / 31,668 / 31,528 B；
   `greedy_flag::decide` 10,388 B → 19,316 / 22,468 / 24,328 B。
3. 12 个构建参数变体都没有稳定超过 baseline：thin/fat/no-LTO、`target-cpu=native`、
   `-pgso=false`、`-hot-cold-split=false`、ext-TSP、`-disable-block-placement`、
   `inline-threshold=0`、单场景 profile。最差的是 no-LTO（慢约 40%）和单场景 profile（慢约 48%）。
4. 输出正确性不变：同一批 20 局 3 队回放，baseline 与 PGO1/2/3 所有产物 SHA-256 完全一致。
5. 热点非常集中：**AI 76.7% / sim 18.8% / hashbrown 2.7%**；
   `bfs_dist_field` 53.4%、`can_stand` 18.9%、`is_walkable` 11.3%、`in_any_base` 6.8%。

## 2. 环境与方法

- 源码：`c6fdc71`；rustc 1.99.1 / LLVM 23.1.1；系统 `llvm-profdata` 23.1.3
- 主机：Linux `aarch64`，8 CPU；CPU 0–3 为 1.53GHz 小核，4–7 为 2.15–2.62GHz 大核
- 基准：钉 CPU 7（大核）、`--jobs 1`；`jobs0` 场景不钉核
- release profile：`lto = "thin"`、`codegen-units = 1`

每轮流程：

```bash
# 插桩
CARGO_TARGET_DIR=target/pgo/r1-instr CARGO_BUILD_JOBS=4 \
RUSTFLAGS="-Cprofile-generate=$PWD/out/pgo/round1/raw" \
./scripts/cargo build --release -p cli

# 训练（每个进程必须用不同的 LLVM_PROFILE_FILE，否则默认文件名会覆盖）
LLVM_PROFILE_FILE=$PWD/out/pgo/round1/raw/a.profraw \
  taskset -c 7 target/pgo/r1-instr/release/qfr run ... --created-time none

# 合并
/usr/sbin/llvm-profdata merge -o out/pgo/round1/merged.profdata out/pgo/round1/raw/*.profraw

# profile-use
CARGO_TARGET_DIR=target/pgo/r1-use CARGO_BUILD_JOBS=4 \
RUSTFLAGS="-Cprofile-use=$PWD/out/pgo/round1/merged.profdata -Cllvm-args=-pgo-warn-missing-function" \
./scripts/cargo build --release -p cli
```

基准用 CPU user+sys 时间，先 warmup，再交替 binary 顺序；指标是 **paired ratio**
（同一 rep 内 `PGO / baseline`，取中位数），>1 表示 PGO 更慢。

## 3. 三轮结果

| 版本 | 累计训练局数 | profile 总计数 | 二进制大小 | `raider::decide` | core40 paired ratio |
|---|---:|---:|---:|---:|---:|
| baseline | 0 | — | 1,687,888 B | 12,992 B | 1.000 |
| PGO1 | 480 | 23,840,410,122 | 1,627,968 B | 30,340 B | 0.98–1.17（多数 ≈1.10） |
| PGO2 | 930 | 46,718,339,498 | 1,627,872 B | 31,668 B | **1.472** |
| PGO3 | 1380 | 66,301,993,595 | 1,628,536 B | 31,528 B | **1.529** |

`core40` = 40 局 2p `raider` vs `greedy_flag`、300 ticks、`--replay-sample none`、`--jobs 1`。
训练集覆盖 2p/3p、15/25/35 地图、per-match/fixed/fixed-random、replay all/none、jobs 0/1。

## 4. 参数 ablation

统一用 PGO1 的 profile，只改一个构建参数；数值为 core40 paired ratio：

| 变体 | 参数 | ratio | 结论 |
|---|---|---:|---|
| `pgo1_thin` | 默认 thin LTO | 1.10 | 最好的 PGO，但仍无稳定收益 |
| `pgo1_fat` | `LTO=fat` | 1.14 | 更差 |
| `pgo1_nolto` | `LTO=false` | 1.40 | 明显更差 |
| `pgo1_native` | `-Ctarget-cpu=native` | 1.19 | 更差（大小核异构） |
| `pgo1_nopgso` | `-pgso=false` | 1.12 | 无改善 |
| `pgo1_nohotcold` | `-hot-cold-split=false` | 1.13 | 无改善 |
| `pgo1_tsp` | ext-TSP block placement | 1.16 | 无改善 |
| `pgo1_noplace` | `-disable-block-placement` | 1.15 | 无改善 |
| `pgo1_noinline` | `inline-threshold=0` | 1.10 | 无改善 |
| `pgo_target_profile` | 只用核心场景训练 | 1.48 | 过拟合，最差 |
| `baseline_fat` | 无 PGO，fat LTO | core40 0.964；core200 1.20 | 不稳定，不采用 |
| `baseline_native` | 无 PGO，native | 1.05–1.22 | 无稳定收益 |

## 5. 场景矩阵（baseline vs PGO1）

4 reps + warmup，`paired ratio` 为该场景内 PGO1 / baseline 的每-rep 中位数：

| 场景 | baseline 中位 CPU(s) | PGO1 中位 CPU(s) | paired ratio |
|---|---:|---:|---:|
| core_200（200 局 2p） | 10.002 | 9.329 | 0.967 |
| 2p raider vs greedy | 2.182 | 2.054 | 0.980 |
| 2p raider vs random + replay | 0.457 | 0.488 | 1.068 |
| 3p mixed | 1.566 | 1.858 | **1.121** |
| 2p random vs random | 0.136 | 0.130 | 0.966 |
| fixed-random（同图） | 1.594 | 1.945 | **1.198** |
| map15 | 1.056 | 1.024 | 0.816 |
| map35 + 3p | 2.162 | 2.525 | **1.174** |
| short60（80 局 ×60 ticks） | 0.917 | 0.860 | 1.174（短场景噪声大） |
| jobs0（多核吞吐） | 4.888 | 5.836 | **1.193** |

结论：有好有坏，3p、同图固定、35×35 大地图、多核吞吐都慢 12–20%；
没有“全场景稳定变快”的证据。

## 6. 热点（round3，按基本块执行计数）

| 函数 | 占比 |
|---|---:|
| `ai::common::bfs_dist_field` | **53.44%** |
| `ai::common::can_stand` | **18.86%** |
| `<sim::ai::MapView>::is_walkable` | **11.35%** |
| `<sim::ai::MapView>::in_any_base` | **6.84%** |
| `HashMap<Coord, ()>::contains_key` | 2.27% |
| `ai::common::base_cells` | 1.68% |
| `ai::common::has_line_of_sight` | 1.08% |
| `<RaiderAi as TeamAi>::decide` | 0.97% |
| `<Sim>::run_tick` | 0.27% |

前四项合计约 **90.5%**，全部是 AI 寻路/合法性判断；`sim` 侧最大的是 `run_tick` 0.27%。
这说明引擎不是瓶颈，AI 决策才是。

**口径说明**：这里是函数内所有基本块计数器之和，近似“执行过的基本块次数”，
不是墙钟时间。本机 `perf` 不可用（`perf_event_paranoid=3`，无硬件 PMU 事件），
所以用 profile 计数作为热点代理。详细 Top 40 与模块聚合在本地
`out/pgo/hotspots-summary.md` 和 `out/pgo/roundN/hotspots.md`。

## 7. 降频/热噪声对照（重要）

实验期间设备在充电、agent 循环也在跑，`cluster2` 温度约 **79–89°C**，
CPU7 的 `scaling_max_freq` 被压到 1.93GHz（`cpuinfo_max_freq` 2.15GHz），
绝对耗时会明显漂移。为了确认 PGO 的差距不是热噪声，做了顺序反转对照：

| rep 内顺序 | baseline | PGO1 | PGO3 |
|---|---:|---:|---:|
| baseline 先跑，PGO3 最后 | 1.063s | 1.225s | 1.671s |
| PGO3 先跑，baseline 最后 | 1.076s | 1.221s | 1.650s |

PGO3 即使每轮第一个跑仍然 ~1.65s；baseline 即使最后跑仍然 ~1.08s。
所以 **PGO2/3 的 50% 级差距不是降频/顺序造成的**，而是代码膨胀。
PGO1 的 ~14% 方向也稳定，但绝对秒数会随频率变化，不能当成精确值。
热点计数是确定性的，不受降频影响。

## 8. 正确性

20 局 3 队、120 ticks、保存全部回放，baseline / PGO1 / PGO2 / PGO3 的
`manifest.json`、`summary.json`、`matches.jsonl`、每份 `replays/*.jsonl`
SHA-256 全部一致。PGO 没有改变数值结果。
